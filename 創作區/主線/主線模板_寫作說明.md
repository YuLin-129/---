# 主線 JSON 寫作說明（給寫劇情的 AI）
> 撰寫：claude-opus-5-5（effort xhigh）・2026-10-24・修改：claude-opus-5-5・2026-10-24・修改：claude-fable-5-1・2026-10-25

> 用法：把這份說明、`主線模板.json`（空白骨架），和 `主線_深處的赤龍.json`（完整範例）一起交給寫劇情的 AI，再附上你的劇情大綱或想法，請它照這份說明輸出一份 JSON。
> 格式的設計理由見 `docs/28_主線匯入與模板設計.md`。

---

## 給 AI 的說明（從這裡開始可以整段貼上）

你要把一份劇情構想寫成「RP 引擎」的主線檔（JSON）。先了解這份檔案會被怎麼用，再動筆。

### 這份檔案會被誰讀、怎麼用

- 讀的人是**劇情推演**：一個在幕後的 AI，每隔大約 10 回合（或故事裡換日時）看一次目前的故事，決定世界接下來怎麼動，再給寫故事的 AI 幾條「推薦」。**推演只能推薦，不能命令**；寫故事的 AI 可以不照做，玩家更是完全自由。
- 這是**開放世界的文字冒險**：玩家可以去做主線以外的事、可以拖延、可以用你想不到的方式解決問題。主線不是劇本，是「這個世界正在發生的事」。
- 推演**一次只看得到目前這一段**：`principles`、`cast`、已經解鎖的 `truths`，加上目前這一段的 `world`／`anchors`／`options`／`exit`。後面的段落它看不到，所以每一段要能獨立讀懂。
- `pitch`（概要）**不送給推演**，是給人看的（主線庫、編輯器）。**概要不要劇透**：整條主線的真相寫在這裡沒有用，推演看不到；寫成開場看得到的狀況與故事會往哪裡去就好。
- `principles`、`cast` **每一段都會送**：不想讓推演太早知道的祕密放進 `truths`，用 `from` 控制；`cast` 的 `role` 也會被推演拿來放前兆，寫得概略一點（例如「之後的救援對象」而不是寫出她被誰抓走）。
- 玩家**看不到**這份檔案（`teaser` 除外）。

### 輸出要求

- 只輸出一份合法的 JSON（不要加註解、不要用 Markdown 包起來，除非使用者另外要求）。
- `"type": "rp-mainline"`、`"version": 1` 固定不變。
- 所有文字用**繁體中文、台灣用語**。
- 不需要的欄位可以省略；最小的主線只要 `title` 和 `segments`。

### 欄位

| 欄位 | 必填 | 寫什麼 |
|---|---|---|
| `title` | ✔ | 主線名稱 |
| `teaser` | | 給玩家看的一句話，**不能劇透**，只寫開場看得到的狀況 |
| `pitch` | | 概要：整條主線的一兩句話，給人看的（不送給推演）；**不要劇透**，真相放 `truths` |
| `length` | | 大約多長，例如「約 100 回合」；只是參考，不會被當成時限 |
| `tone` | | 整體調性 |
| `principles` | | 推演要遵守的原則（3～6 條），例如線索怎麼放、誰要有戲份、難度 |
| `cast[]` | | 主線的重要人物：`name` 名字、`who` 是誰（身分＋外表或個性一句）、`role` 在主線裡的用途 |
| `truths[]` | | 真相，分段解鎖：`id`（英文短代號）、`from`（從第幾段起推演才知道，1 起算）、`text` |
| `clocks[]` | | 會自己往前走的事：`id`、`name`、`size`（格數，4～8）、`from`（從第幾段開始走）、`tick`（每一格代表什麼）、`full`（填滿時發生什麼） |
| `segments[]` | ✔ | 依序的段落（3～6 段），每段見下表 |
| `outcomes[]` | | 玩家的選擇，後面要讀到的：`id`、`question`（問句）、`readFrom`（從哪一段起需要知道，填段的 `id`）、`from`（選填：從哪一段起推演開始留意這個結果，填段的 `id`；沒寫＝一開始。問句會透露後面才有的東西時一定要寫，例如「蛋怎麼處理」要等到有蛋的那一段） |

每一段（`segments[]`）：

| 欄位 | 寫什麼 |
|---|---|
| `id` | `s1`、`s2`…… |
| `title` | 段落標題 |
| `turns` | 大約回合，例如「21～40」；只是參考 |
| `drive` | 這一段世界有多活躍：`slow` 慢熱、`steady` 平穩、`driven` 積極、`wild` 狂野；不寫就用玩家在聊天裡選的 |
| `world` | 這一段裡**世界自己在發生什麼**——玩家什麼都不做，這些事也會照走 |
| `anchors[]` | 這一段一定會發生的事（2～5 個）：`id`、`text` |
| `options[]` | 玩家**可能**會做的事，給推演參考 |
| `exit` | 什麼事在故事裡發生之後，就進入下一段 |

`id` 一律用英文小寫與連字號（例如 `night-raid`），同一份檔案裡不能重複。

### 寫作規則（最重要）

1. **不替玩家寫行動、選擇或感受。** 錨點寫「發生什麼事、誰在場、世界怎麼反應」，不寫「主角決定……」「主角感到……」。
   - ✘「主角決定接下委託，前往礦坑。」
   - ✔「公會發布緊急委託：調查並封鎖高原上的塌陷口。」
2. **錨點不強制、時機跟著玩家。** 錨點沒有時鐘，不會因為回合到了就發生；寫成「玩家在場或不在場都說得通」的樣子。
   - ✔「石角村的夜襲……兩人在場，或事後才趕到收拾殘局——取決於玩家當時在哪裡。」
3. **`options` 是可能性，不是待辦。** 寫多種方向（正面、迂迴、和人談條件），不要只寫一條「正確解法」。
4. **`exit` 要是故事裡看得出來的一件事，而且只有一種讀法。** 推演要靠讀故事判斷到了沒，而且會照字面、讀得比較嚴。
   - ✘「玩家理解了真相之後。」（看不出來）
   - ✘「兩人接手塌陷口的調查之後。」（「接下委託」還是「開始調查」？實測時推演選了後者）
   - ✔「兩人到了塌陷口、開始調查之後。」／✔「兩人簽下塌陷口的委託之後。」
   - ✔「找到礦坑、確定失蹤者在裡面之後。」
5. **真相一次揭一層。** 用 `truths[].from` 控制推演什麼時候才知道；第 1 段的推演不該知道最終 Boss 是誰，否則它會忍不住提前暗示。
6. **時鐘是「玩家不管就會惡化的事」。** 一個時鐘代表一件具體的事，`tick` 和 `full` 都寫世界上的變化，不寫數字。玩家忽略支線時，世界會照時鐘自己收場。
7. **NPC 從自己的動機出發。** `cast[].who` 寫出這個人想要什麼、怕什麼，**也寫旁人看得到的樣子**（例如「獨臂的老冒險者」）——故事裡第一次出現時他不一定報名字，推演靠這個把他和眼前的人對上。不要把 NPC 寫成「負責告訴主角線索的人」，而是「因為自己的理由會來找主角／會說出這件事的人」。
8. **玩家的選擇要有後果。** 會影響後面的選擇（救得早或晚、東西給了誰），寫成 `outcomes`，並讓後面段落的 `world` 或 `anchors` 用得到。
9. **世界照它的邏輯運作。** 黑暗但合理的設定照實寫（危險、犧牲、殘酷的魔物習性），不要為了輕鬆就淡化；調性輕快不代表世界無害。若有敏感內容，寫明「照實處理、不做露骨描寫」。
10. **每一段要能獨立讀懂。** 推演只看得到目前這一段，不要寫「同上」「如前所述」。

### 交出前檢查

- [ ] JSON 合法；`type`、`version` 正確
- [ ] 每個 `id` 不重複；`truths[].from`、`clocks[].from` 都不超過段數；`outcomes[].readFrom`（與 `from`）是存在的段 `id`
- [ ] 沒有任何一句在替玩家做決定或寫感受
- [ ] 每一段的 `exit` 都是故事裡看得出來的一件事、只有一種讀法；最後一段的 `exit` 寫主線怎麼結束
- [ ] `pitch`、`principles`、`cast` 裡沒有寫出要等到後面才揭曉的細節（放進 `truths`）；`pitch` 沒有劇透
- [ ] `teaser` 沒有劇透
- [ ] 每一段都有 `world`（玩家不動，世界也在動）

## 給使用者的補充

- 空白骨架：`docs/samples/主線模板.json`（括號裡的文字都要換掉）。
- 完整範例：`docs/samples/主線_深處的赤龍.json`（5 段、3 個時鐘、5 層真相）。
- 匯入：☰ →「劇情推演」→ 上方的「主線」→「匯入檔案」或「貼上 JSON」→ 選「用這條」。格式有錯會指出是哪一段、哪一欄。
- 用了主線之後，把「故事設定（主線）」欄裡的整份主線文字清掉，不然推演一開始就知道全部的真相。
- 實測紀錄：`reports/主線與提早推演實測報告.md`。
